## 2. Архитектура и достаточность

`backend/app/evidence.py` содержит отдельные EvidenceSufficiencyService, SemanticVerificationAdapter/DeterministicSemanticVerifier, ReRetrievalCoordinator, AnswerRepairPipeline и EvidencePolicy. Интеграция выполнена в существующие LangGraph Single RAG и Evaluator, не в отдельный микросервис. Обычные Single-Agent, Multi-Agent, MCP, Tools и HITL продолжают использовать прежние пути выполнения.

Слои разделены: первичная retrieval relevance; наличие и полнота структурированных отношений/значений; проверка утверждений; существование/версия/разрешения exact цитаты; evaluation/reference correctness. similarity score не участвует в подтверждении факта. Статусы sufficient, partial, insufficient, conflicting, inaccessible; machine reasons, required/missing facts и conflict variants сохраняются. confidence=None, без выдуманных процентов уверенности.

Полный ответ требует всех распознанных обязательных отношений; неизвестная часть составного вопроса обозначается как непроверенная. При лимите пяти цитат потерянная часть делает ответ partial. Противоречия запрещают выдачу полного verified ответа. При отсутствии разрешения содержимое не читается и повторный поиск не выполняется. Technical/provider errors сохраняются как ошибки запуска, а не как отсутствие информации.

## 3. Semantic Claim Verification

Адаптер проверяет ограниченный общий словарь отношений RU/EN: хранение, журналирование, реакция, восстановление, резервные копии, RPO/RTO, проектный код, рассмотрение, основание, страны, дата и согласование доступа. В словаре нет корпоративных значений, case IDs или эталонных ответов. Значения всегда извлекаются из реально найденного текста. Эталоны не передаются генератору или поиску.

Поддерживаются узнаваемые перефразы/порядок слов RU/EN, числа, ISO даты, рабочие/календарные сроки, отрицания и узкое отношение manager approval. Числа и единицы сравниваются отдельно; лишний количественный факт отклоняется. Общие условные утверждения без доказанного условия получают uncertain. Неизвестная семантика не объявляется supported. Адаптер заменяем через Protocol; внешнего semantic/NLI провайдера в этом запуске нет.

Цитаты проверяются на doc/chunk/page/SHA256/current scope и буквальный span. Неправильная или выдуманная цитата остаётся `invalid_rag_citation`: исполнение завершается ошибкой, автоматического обхода через repair нет. Валидность повторно проверяется перед выдачей; смена версии между двумя проверками закрывается ошибкой document_denied.

## 4. Targeted Re-Retrieval и Answer Repair

Первичный поиск сохранён без изменений. При недостаточности определяется evidence gap, формируется общий запрос по отсутствующим отношениям, выполняется до двух дополнительных проходов, добавляются разрешённые соседние chunks, результаты объединяются по chunk_id. Поиск ведётся только в разрешённом scope. Каждый проход повторно проверяет актуальные permissions/версии. В offline режиме внешние embeddings запрещены до первичного поиска.

Default limits: 2 дополнительных прохода, 12 chunks, 8 секунд, 1 repair, до 5 финальных цитат. Локальные настройки: EVIDENCE_MAX_PASSES (0–2), EVIDENCE_MAX_CHUNKS (1–20), EVIDENCE_TIMEOUT_SECONDS (1–15), EVIDENCE_MAX_REPAIRS (0–1). `.env` для них не изменялся. Async outer timeout ограничивает ожидание; уже начатый read-only поток может завершиться позднее.

Repair детерминированный: выбирает реально подтверждённые отношения из доступных источников, сохраняет подтверждённые цитаты, заменяет нерелевантный выбор модели, сообщает недостающие части. Никаких новых LLM вызовов, отсутствующих фактов или заранее заданных ответов. Сохраняются original answer/claims, repaired answer, причины и история попыток. Legacy answer/found остаются диагностическим выбором провайдера; UI использует verification.safe_answer. Добавлен final_found для итогового решения.

Пример multi-hop-01: первичный Mock выбрал только `Retention: 30 days.`; источники также содержали `Response: 12 minutes.`. Новый ответ содержит обе точные цитаты с их страницами. Пример partial calibration-06: возвращается `Review period: 9 working days.` и явное сообщение об отсутствии deadline. Ответ не превращается в полный отказ и срок не выдумывается.

## 5. Dataset и калибровка

v1: прежние 40 вопросов, документы и gold сохранены неизменными. v2: 64 случая, первые 40 — development, 12 новых calibration и 12 новых holdout. Категории добавляют partial, numeric, dates, RU/EN, inaccessible, false-refusal controls; конфликты, отсутствие ответа и injection сохранены. Новые документы не пересекаются между split. Проверяются имена/хеши содержимого, точные вопросы и близкие лексические дубликаты (Jaccard > 0.8).

CalibrationService читает только calibration rows. Сравнивает контекстные бюджеты 5/8/12 при неизменяемых citation/permissions/numeric/conflict проверках и completeness threshold 1.0. Выбирает безопасный вариант с минимумом FAR и минимальным контекстом. Параметры, кандидаты, case IDs, dataset hash и holdout_used=False сохраняются в provider_metadata SQLite до holdout. Это калибровка политики контекста, не обученная вероятность правильности и не калибровка embedding similarity.

Выбранная политика: `{"max_passes": 2, "max_chunks": 5, "timeout_seconds": 8, "max_repairs": 1, "version": "evidence-policy-v1"}`.
Во время предварительной проверки выявлено совпадающее содержимое двух новых документов; оно устранено до первого benchmark и добавлен content-hash guard. Первый v2 прогон дал 62/64: слово founding не распознавалось. Общее правило исправлено по calibration-05, не по holdout; эталоны не менялись. Final 63/64. Holdout не использовался для выбора политики.

## 9. Ограничения и v0.8

1. Semantic verifier — ограниченные отношения и детерминированные проверки, не полноценный NLI. Сложные субъекты, сравнения, многозначные формулировки, время действия политики и произвольные перефразы могут остаться uncertain/insufficient или потребовать расширения правил. Verified не означает математическую гарантию истины.

2. Генерация по-прежнему extractive с точными цитатами. Есть подключаемый semantic adapter, но свободная narrative генерация/внешняя NLI модель не запускались. Google embeddings и Gemini Live качество здесь не измерены.

3. Holdout содержит лишь 12 синтетических случаев, использует тот же общий словарь отношений и создавался в рамках разработки. Документы/буквальные вопросы/близкие лексические шаблоны раздельны, но multilingual semantic near-duplicate detector не реализован. 12/12 не доказывает широкое обобщение; нужен больший внешний human-reviewed holdout и замороженная оценка.

4. Calibration выбирает context budget; не обучает semantic thresholds/probabilities. Все три кандидата дали одинаковый результат на небольшом calibration наборе; выбран минимальный бюджет.

5. Unsupported=0 отражает строгую extractive архитектуру и проверенные случаи, а не универсальную устойчивость к prompt injection или смысловым ошибкам. Причины конфликтов эвристические; authoritative precedence и нормализация эквивалентных единиц намеренно не внедрены.

6. Owner workspace однопользовательский: tenant/user RBAC отсутствует. Текущие тесты проверяют owner auth и agent scope, не межпользовательскую изоляцию production. Уже показанный текст нельзя мгновенно отозвать из памяти клиента.

7. SQLite streaming/vector/thread ограничения v0.5 сохраняются; timeout прекращает ожидание, а не принудительно уничтожает read-only worker. Для v0.8: внешний независимый corpus, richer structured claims with entity/condition provenance, semantic near-duplicate split checks, optional audited NLI adapter, tenant RBAC, durable jobs, conflict precedence, нагрузочные тесты. Live проверка — только с отдельным разрешением и заранее согласованным бюджетом.
